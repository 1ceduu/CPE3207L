\section*{Manuscript Review}
\textbf{Overall assessment.} The draft addresses an important problem and has a clear practical direction, but the current manuscript is not yet technically publishable because (i) the source does not compile from a clean build, and (ii) core technical claims (automated detection, reliability, and monitoring performance) are stated without methods or validation evidence in the included sections.

\section*{Technical findings (priority first)}
\begin{enumerate}[leftmargin=*,label=\textbf{T\arabic*.}]
  \item \textbf{Classification: definite error}\\
  \textbf{Location:} \texttt{TimTissis.tex}, preamble package block (lines 8, 18, 19).\\
  \textbf{Problem:} The document loads \texttt{algorithmic}, \texttt{algpseudocode}, and \texttt{algorithm2e} together, which triggers \texttt{LaTeX Error: Command \textbackslash algorithmic already defined}. A clean compile with \texttt{pdflatex -halt-on-error} stops with a fatal error.\\
  \textbf{Why it matters:} The manuscript is not reproducibly buildable from source, which blocks submission and collaboration.\\
  \textbf{Suggested fix:} Keep one algorithm package family only. For example, remove \texttt{\textbackslash usepackage\{algorithmic\}} if \texttt{algpseudocode} is retained, or remove \texttt{algpseudocode}/\texttt{algorithm2e} if \texttt{algorithmic} is preferred.

  \item \textbf{Classification: unsupported claim}\\
  \textbf{Location:} Abstract (\texttt{TimTissis.tex}:48) and omitted body sections (\texttt{TimTissis.tex}:59--60).\\
  \textbf{Problem:} The abstract states that the paper ``presents the design and development'' and ``offers a reliable and scalable solution,'' but the included manuscript contains introduction/problem/objectives/scope/significance only; methodology and evaluation sections are commented out.\\
  \textbf{Why it matters:} Claim strength exceeds evidence shown in the manuscript.\\
  \textbf{Suggested fix:} Either (a) downscope claims to a proposal/design concept, or (b) include methodology, implementation details, and quantitative validation results that justify reliability/scalability claims.

  \item \textbf{Classification: likely issue (implementation ambiguity)}\\
  \textbf{Location:} \texttt{Section2.tex}:5 and \texttt{Section5.tex}:11.\\
  \textbf{Problem:} ``Rolling time window,'' ``defined standard,'' and alerting logic are not mathematically specified (window length, baseline estimator, threshold rule, update cadence, hysteresis, or false-alarm handling).\\
  \textbf{Why it matters:} The central health-monitoring contribution cannot be reproduced or implemented consistently.\\
  \textbf{Suggested fix:} Add a precise decision rule (equations or pseudocode), including baseline computation, deviation metric, thresholding, and alert state transitions.

  \item \textbf{Classification: likely issue (units/definitions)}\\
  \textbf{Location:} Abstract (\texttt{TimTissis.tex}:48), \texttt{Section2.tex}:5, \texttt{Section4.tex}:10.\\
  \textbf{Problem:} Air-quality monitoring is described, but measured variables and safe limits are undefined (e.g., NH$_3$, H$_2$S, CO$_2$, units, calibration procedure, sensor placement, and sampling interval).\\
  \textbf{Why it matters:} Without explicit quantities and units, ``toxicity alerts'' are not technically auditable and may be misinterpreted in deployment.\\
  \textbf{Suggested fix:} Define each monitored variable, unit, threshold source, sensor specification, calibration method, and alert trigger condition.

  \item \textbf{Classification: unsupported claim}\\
  \textbf{Location:} \texttt{Section5.tex}:11.\\
  \textbf{Problem:} The text claims planned validation ``will characterize detection reliability'' but no validation protocol, ground truth definition, or performance metrics are provided in the manuscript body.\\
  \textbf{Why it matters:} Reliability statements are currently non-falsifiable.\\
  \textbf{Suggested fix:} Add a validation subsection defining labeled health events, evaluation window, and metrics (e.g., sensitivity, precision/PPV, false-alert rate, and time-to-alert).

  \item \textbf{Classification: likely issue (notation/terminology drift)}\\
  \textbf{Location:} Abstract (``eliminating reliance on \ldots wireless communication,'' \texttt{TimTissis.tex}:48), \texttt{Section4.tex}:9, \texttt{Section5.tex}:11.\\
  \textbf{Problem:} Connectivity terminology is not stable: ``hardwired'' and ``independent from internet connectivity'' appear alongside sensitivity to ``network connectivity'' interruptions, without clarifying whether this means local wired bus vs internet backhaul.\\
  \textbf{Why it matters:} Ambiguity affects reliability and deployment assumptions.\\
  \textbf{Suggested fix:} Explicitly separate local wired module network behavior from internet dependence, and state which functions degrade under each failure mode.
\end{enumerate}
