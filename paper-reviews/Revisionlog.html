RECOMMENDATION/ COMMENTS/ ANNOTATIONS:

[Include recommendations during deliberation, comments and annotations from individual panel members on the manuscript]

  1. In Section VII (Methodology), Edge Node Firmware (ESP32), "How it is implemented" bullet (Page 6, Paragraph 2): "Core 0 is dedicated strictly to hardware interrupts… ensuring no data is lost during execution delays."  — Panel Comment: How can you be so sure? What if the hardware fails? Use better wording if it cannot be proven.

    Response: [Overly absolute claim softened to reflect realistic firmware guarantees]

    Thank you for pointing this out. I/We agree with this recommendation. Therefore, I/we have revised the phrasing from "ensuring no data is lost during execution delays" to "minimizing the risk of missed sensor readings during execution delays." This change acknowledges that while the dual-core FreeRTOS architecture significantly reduces the likelihood of missed readings by dedicating Core 0 exclusively to hardware interrupt processing, absolute data integrity cannot be guaranteed in the event of physical hardware failure. The revised language more accurately reflects what the firmware design achieves in practice without overpromising. This change can be found in Section VII (Methodology), Edge Node Firmware (ESP32) subsection, "How it is implemented" bullet, Page 6, Paragraph 2.

  2. In Section VII (Methodology), Test 1.1 – Feed Dispensing Accuracy (FDA), Pass Criterion (Page 14): "Mean FDA across all 30 trials ≥ 95%."  — Panel Comment: How did you settle on the 95% accuracy?

    Response: [Justification added with supporting literature in both the Quantitative Metrics definition and the Test 1.1 Pass Criterion]

    Thank you for pointing this out. I/We agree with this recommendation. Therefore, I/we have expanded the Pass Criterion for Test 1.1 to include an explicit justification for the 95% (±5%) threshold. The revised text explains that this threshold is adopted from accuracy benchmarks reported in comparable automated feeding and precision livestock systems. Specifically, auger-based pig feeding systems in published literature have demonstrated dispensing errors as low as 0.25% average and 1.5% maximum [Zhang et al., 2025; Adeoye et al., 2025; Dingcong et al., 2017]. Furthermore, a ±5% tolerance was selected because granular feed flow through auger mechanisms can exhibit inherent discharge variability of approximately 5% due to hopper–conveyor coupling parameters [Chen et al., 2024; Tangorra et al., 2018], while still remaining within nutritionally acceptable dispensing limits for swine rations. The same justification was also added to the Quantitative Metrics definition of FDA in Section VII. This change can be found in Section VII (Methodology), Quantitative Performance Metrics subsection (FDA definition) and Test 1.1 Pass Criterion, Page 14.

  3. In Section VII (Methodology), Objective 3 heading and Test 3.1 – Data Display Latency explanation (Page 14): The text used the term "real-time sensor data" and "real-time monitoring," while the pass criterion previously allowed individual readings up to 5 seconds.  — Panel Comment: How real-time is the monitoring when it takes a delay of up to 5 seconds? Either get rid of "real-time" or improve the delay.

    Response: [Terminology updated to "near-real-time" and maximum individual delay tightened from 5 s to 3 s]

    Thank you for pointing this out. I/We agree with this recommendation. Therefore, I/we have made two related changes: (1) the term "real-time" has been replaced with "near-real-time" throughout the Objective 3 heading and the Test 3.1 explanation, and (2) the maximum individual reading threshold was tightened from 5 seconds to 3 seconds, with the mean target remaining ≤ 2 seconds. The revised explanation now also cites published evidence — IoT-based swine monitoring systems have demonstrated dashboard response times of under 1 second in production environments [He et al., 2024] — validating that the ≤ 2-second mean threshold is both achievable and appropriate for livestock health monitoring. The revised description now reads: "near-real-time monitoring with sufficiently low delay for practical farm supervision." This change can be found in Section VII (Methodology), Objective 3 heading, and Test 3.1 Pass Criterion and explanation, Page 14.

  4. In Section VII (Methodology), Test 3.3 – System Uptime (Usys), Pass Criterion (Page 14): "Usys ≥ 95%."  — Panel Comment: How was this decided? Either look through related literature or justify.

    Response: [Justification added with IoT industry standard literature in both the Quantitative Metrics definition and the Test 3.3 Pass Criterion]

    Thank you for pointing this out. I/We agree with this recommendation. Therefore, I/we have expanded the Pass Criterion for Test 3.3 to include an explicit justification for the Usys ≥ 95% threshold. The revised text states that this threshold aligns with IoT industry standards that commonly require at least 95% availability for embedded monitoring systems [Tibreza et al., 2023; Carvalho et al., 2023], where continuous sensor coverage is necessary but brief, recoverable interruptions (e.g., software restarts) are acknowledged as acceptable. A concrete operational basis was also added: at 95% over a 72-hour trial, this permits a maximum cumulative downtime of approximately 3.6 hours — a ceiling beyond which monitoring gaps become operationally significant in a farm health management context. The same justification was also added to the Quantitative Metrics definition of Usys in Section VII. This change can be found in Section VII (Methodology), Quantitative Performance Metrics subsection (Usys definition) and Test 3.3 Pass Criterion, Page 14.

Changes can be found throughout Section VI (Review of Related Literature) and Section VII (Methodology), with new entries documented in reference.bib.
